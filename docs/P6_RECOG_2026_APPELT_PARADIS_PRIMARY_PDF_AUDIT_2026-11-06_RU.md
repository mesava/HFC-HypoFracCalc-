# HFC — P6.ReCOG: первоисточниковая проверка нового оригинального консенсуса ReCOG 2026

**Дата:** 6 ноября 2026 года. **Результат:** оригинальная публикация идентифицирована побайтово, сверены рекомендации на PDF стр.2–6 (с визуальной проверкой алгоритма Figure 1 и таблицы/рисунка Figure 2). **Коэффициенты и расчётное ядро не изменены.**

## 1. Что именно прислали

**Важное библиографическое разграничение:** в HFC `src/data/evidence/v0.1/sources.ts` уже содержится **эта же** запись `paradis-2026-recog-consensus` с правильным DOI/PMID. ## 2. Ключевые рекомендации из оригинала

- **PDF p.2 / e102, Scope:** документ намеренно **не предписывает конкретный метод дозовой аккумуляции, числовые ограничения OAR или клиническое решение**. Нельзя выдавать ReCOG за источник новых `TRF` или `Dmax` cutoff.
- **PDF p.3 / e103, Equieffective dose:** `EQDX = D × (D/n + α/β)/(X + α/β)`, где `D/n` относится к конкретному вокселю и его реальной фракционной дозе, а не автоматически к общей рецептурной дозе. **Последовательные (non-concurrent)** фазы конвертировать **отдельно**, затем суммировать EQDX; для **одновременно действующих на тот же воксель** планов сначала объединять соответствующие суточные дозы, затем отдельно считать их биологический эффект. Скалярный HFC пока не подтверждает корректную voxel-wise модель одновременно накладывающихся планов.
- **PDF p.3 / e103, TRF:** `tissue recovery factor` — предположение о восстановленной доле эффекта ранее облучённого OAR; корректирующий множитель на **предыдущую эквивалентную дозу** равен `1 − TRF`. Не применять к текущему курсу и не устанавливать TRF автоматически по длительности интервала; авторы подчёркивают недостаточность знаний для многих тканей.
- **PDF p.4 / e104, Figure 1:** сначала определяется клиническая обеспокоенность кумулятивными побочными эффектами; затем — доступность DICOM-RT, качество регистрации и возможность 3D накопления EQDX. При ненадёжных данных допускается точечная оценка; выбор способа не заменяет QA регистрации.
- **PDF p.5 / e105, Table:** для ситуаций с clinically relevant concern рекомендованы импорт данных, комиссионированная регистрация (если файлы доступны), оценка регистрационной неопределённости и точности OAR-контуров, расчёт кумулятивной дозы как минимум одним методом. В ситуации без concern ряд пунктов **optional**, а оценка перекрытия остаётся recommended.
- **PDF p.5 / e105, dose accumulation:** обычно предпочтительна пространственная регистрационно-зависимая сумма в эквивалентной дозе. Точечное суммирование околомаксимальных доз может быть обосновано отсутствием DICOM, неадекватной регистрации, существенным градиентом или достаточностью консервативной оценки; следует документировать ограниченность пространственного совпадения максимумов.
- **PDF p.6 / e106, Figure 2:** при concerns рекомендовано документировать места и даты RT, Rx/технику/модальность, α/β и TRF, способ регистрации, метод суммирования, неопределённости, **OAR физическую дозу предыдущих и текущего курсов** и **кумулятивную эквивалентную дозу** (с указанием TRF). Также необходимо фиксировать информированное согласие, обсуждение альтернатив и shared decision-making. Визуализация перекрытия и кумулятивные OAR-DVH — optional; для исследовательских когорт по возможности рекомендуется хранить per-plan/3D данные с неопределённостью.

**Подробное построчное сопоставление**: [25-рекомендационный crosswalk](P6_RECOG_2026_25_STANDARD_TO_HFC_CROSSWALK_2026-11-06.csv); `present` 6, `partial` 11, `missing` 8. Это **описательный gap-аудит**, не процент клинического соответствия.

## 3. Текущие ограничения HFC (что действительно умеет)

HFC v0.2-dev сохраняет источник в аудите; использует скалярный EQD₂/BED одной **выбранной метрики OAR**; проверяет согласованность dose metric между курсами; позволяет только ручной `TRF` с обоснованием и только для предыдущего курса; записывает `previousDoseData`, `registrationSuitability`, `strategy`; показывает предупреждение при выборе 3D strategy, **не выдавая скалярную сумму за фактически выполненную 3D аккумуляцию**.

Однако экспортируемый `ReirradiationAuditRecord` пока не является полноценным **Figure 2 ReCOG clinical record**: он не гарантирует даты предыдущих курсов, анатомические сайты/латеральность/рецептурную дозу/модальность, подробную регистрационную QA (ROI, метод, неопределённость), OAR contoured 3D DVHs, informed consent или результаты shared decision-making.

**Обоснованный риск:** наличие аудита JSON, содержащего список курсов и число кумулятивной EQD₂, **не эквивалентно** ReCOG-compliant накоплению дозы для лечения пациента. Отдельная [issue #107](https://github.com/mesava/HFC-HypoFracCalc-/issues/107) определяет будущую типизированную схему отчёта и дополнительные проверки, которые потребуют экспертной приёмки.

## 4. Числовые проверки / ловушки алгоритма

**Контроль 1 — последовательные фазы:** два раздельных курса/этапа на одну условную дозовую метрику, `20Gy/10×2` и `25Gy/5×5` при α/β=3 дают **20+40=60Gy_EQD2**, хотя физическая сумма 45Gy. Если заменить их **фиктивным курсом 45Gy/15×3**, получится **54Gy_EQD2**. Это демонстрирует, почему нельзя конвертировать совокупный `D/n` без учета фракционирования отдельных планов.

**Контроль 2 — одновременно действующие планы в одном вокселе:** два одновременных пучка/плана по 2Gy на один voxel за один сеанс с α/β=3: суммарная суточная доза 4Gy даёт `BED=4×(1+4/3)=9.333…Gy`; фиктивное биологическое суммирование двух независимых `BED(2Gy)=3.333…Gy` даёт `6.666…Gy`. Разница является свойством LQ модели. HFC **не заявляет реализации** пространственной суточной синхронизации планов; этот пример — научный регрессионный антипример, не схема лечения.

**Контроль 3 — TRF:** предыдущие `40Gy_EQD2` с явно выбранным `TRF=0.25` дают сохранённый вклад 30Gy_EQD2; текущие 20Gy_EQD2 добавляются полностью, сумма **50Gy_EQD2**. Для `TRF=0` результат был бы **60Gy_EQD2**. Коэффициент в примере выбран **только для теста арифметики**, ReCOG не рекомендует TRF=0.25 как клиническую величину.

**Вывод:** оригинал поддерживает математические принципы HFC и показывает, что для полноценной клинической отчётности необходимы дополнительные данные, QA и интерфейсы. **Новых α/β, TRF или OAR tolerances в базу не внесено.**
