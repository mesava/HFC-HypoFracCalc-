# Аудит расчётов HFC — v0.2-dev

## Цель

Клинический радиобиологический расчёт должен быть воспроизводимым не только по итоговому числу, но и по исходным данным, выбранным параметрам, доказательной базе и допущениям.

Экспортируемый аудит реализован для четырёх расчётных модулей:

- **Быстрый EQD**;
- **Сравнение режимов**;
- **Перерывы в лечении**;
- **Повторное облучение**.

## Формат

На странице результата каждого поддерживаемого модуля доступна кнопка:

```
Скачать аудит JSON
```

JSON-файл содержит структурированную запись расчёта и предназначен для:

- независимой проверки;
- сохранения вместе с локальной документацией;
- последующего сравнения расчётов;
- воспроизведения результата после обновления HFC;
- машинного анализа без извлечения данных из интерфейса.

## Что сохраняется

Общие поля версии v0.2-dev:

- версия схемы аудита;
- версия расчётного ядра HFC;
- версия доказательной базы и дата отсечения данных;
- дата и время формирования файла;
- идентификатор и название клинического исхода;
- выбранные биологические параметры и способ их выбора;
- идентификаторы записей и источников, если они есть;
- входные данные расчёта;
- численные результаты;
- предупреждения;
- библиографические записи использованных параметрических и методических источников.

### Быстрый EQD

Дополнительно сохраняются:

- число фракций;
- доза за фракцию;
- физическая доза;
- BED;
- EQD₂;
- диапазон чувствительности по 95% ДИ α/β, если он доступен.

### Сравнение режимов

Дополнительно сохраняются:

- все сравниваемые режимы;
- выбранный референсный режим;
- все клинические исходы;
- α/β отдельно для каждого исхода;
- BED/EQD₂ и физическая доза каждого режима;
- разности относительно референсного режима;
- коррелированный диапазон чувствительности ΔEQD₂, если он доступен.

### Перерывы в лечении

Дополнительно сохраняются:

- режим ввода: календарь или ручная длительность;
- исходный курс;
- календарные даты и нерабочие даты, если использован календарный режим;
- Dprolif и Tk вместе с происхождением;
- пользовательский Tk override, если он применён;
- плановый и фактический OTT;
- базовый сценарий без компенсации;
- компенсация в выходные;
- компенсация двумя фракциями в сутки;
- интервал между BID-фракциями;
- входы и результат радиобиологической компенсации дозой;
- ошибки отдельных стратегий, если конкретная стратегия неприменима;
- все добавленные карточки органов риска;
- для каждого органа риска — дозовая метрика, α/β, T½ и provenance;
- пользовательская или пропорционально масштабированная доза после перерыва;
- ΔBED/ΔEQD₂ для выходных, BID и компенсации дозой;
- некорректные карточки со статусом ошибки вместо их молчаливого исключения.

### Повторное облучение

Дополнительно сохраняются:

- дозовая метрика;
- классификация типа I / II;
- наличие геометрического перекрытия;
- наличие опасения по кумулятивной токсичности;
- качество предыдущих данных;
- пригодность регистрации;
- способ оценки кумулятивной дозы;
- все предыдущие курсы и текущий курс;
- интервалы между курсами;
- ручные допущения о восстановлении и их обоснование;
- BED и EQD₂ каждого курса;
- скорректированный вклад каждого предыдущего курса;
- кумулятивные BED и EQD₂;
- остаточный EQD₂-бюджет, если пользователь его рассчитывал;
- специальная проверка HyTEC для повторного облучения спинного мозга, если она применялась.

## Печатный отчёт

Для тех же четырёх модулей рядом с JSON-экспортом доступна кнопка:

```
Печатный отчёт
```

HFC открывает отдельную человекочитаемую страницу с:

- названием модуля;
- версиями расчётного ядра, доказательной базы и схемы аудита;
- исходными параметрами;
- ключевыми результатами;
- таблицами сравнения;
- предупреждениями;
- библиографией;
- явным предупреждением о назначении инструмента.

В отчёте есть кнопка **«Печать / сохранить PDF»**. PDF создаётся стандартным механизмом печати браузера, поэтому HFC не передаёт данные на внешний сервис и не требует серверного генератора PDF.

Макет содержит отдельные стили для A4 и печати. Пользовательские названия режимов и другие редактируемые строки экранируются перед вставкой в HTML.

## Почему источники копируются в файл

В отчёте сохраняются не только идентификаторы источников, но и их библиографические записи.

Это нужно для того, чтобы исторический расчёт оставался понятным даже после обновления реестра доказательной базы.

## Версионирование

В файл входят два независимых номера:

```
engineVersion
evidence.datasetVersion
```

Также сохраняется:

```
schemaVersion
```

Версия схемы аудита относится к структуре JSON-файла и может меняться независимо от расчётного ядра.

## Что намеренно не сохраняется

HFC не требует и не добавляет в файл:

- ФИО пациента;
- дату рождения;
- номер истории болезни;
- идентификаторы медицинской информационной системы.

Текущий аудит рассчитан на радиобиологические параметры и методику расчёта, а не на хранение персональных данных.

Если пользователь самостоятельно включает идентифицирующие данные в свободный текст будущих версий, ответственность за их обработку должна определяться локальными правилами учреждения.

## Время формирования

Поле `generatedAtIso` добавляется только в момент нажатия кнопки экспорта.

Оно не участвует в математическом расчёте. При фиксированной временной метке сама сериализация детерминирована и проверяется тестом.

## Контроль целостности audit JSON

Начиная с audit-integrity v0.1 скачиваемый JSON больше не является «голой» записью schema `1.0`. Сама клиническая запись **не изменяется**, а помещается во внешний versioned envelope:

```json
{
  "format": "hfc-audit",
  "envelopeVersion": "1.0",
  "record": {
    "schemaVersion": "1.0"
  },
  "integrity": {
    "algorithm": "SHA-256",
    "canonicalization": "hfc-json-v1",
    "digestHex": "..."
  }
}
```

Хеш вычисляется только по полю `record` после детерминированной канонизации JSON. Ключи объектов сортируются, порядок массивов сохраняется, `undefined`-поля не участвуют, а нечисловые значения не переписываются.

Это означает, что перестановка ключей при повторной сериализации не меняет digest, но изменение любого значения внутри audit record приводит к несовпадению SHA-256.

### Обратная совместимость

Старые raw audit JSON schema `1.0` без envelope остаются читаемыми и классифицируются как:

`legacy-unverified`

Новые envelope-файлы после успешной проверки SHA-256 получают статус:

`verified`

Legacy-файл не считается повреждённым, но HFC не может криптографически подтвердить, что его содержимое не менялось после экспорта.

### Что SHA-256 не доказывает

SHA-256 здесь является **контролем целостности, а не цифровой подписью**. Он не подтверждает автора файла и не устанавливает юридическую принадлежность расчёта конкретному пользователю или учреждению.

## Ограничения текущего этапа

Карточки органов риска в модуле «Перерывы в лечении» входят в общий аудит. Если карточка содержит некорректный или неполный ввод, она **не исчезает** из аудита: сохраняются исходные строки и текст ошибки со статусом `input-error`.

Реализованы:

1. детерминированная канонизация audit record;
2. SHA-256 envelope;
3. проверка целостности;
4. чтение legacy schema 1.0 как `legacy-unverified`;
5. отказ от неизвестных envelope/schema/module.

## Import / replay v0.1

В HFC добавлена отдельная страница **«Проверка аудита»**. Файл читается локально в браузере и не отправляется на внешний сервер.

Последовательность проверки:

1. разобрать JSON;
2. для нового envelope проверить SHA-256;
3. определить module/schema/engine/evidence version;
4. восстановить исходные параметры;
5. повторно выполнить расчёт текущим движком;
6. сравнить клинически значимые поля сохранённого и пересчитанного audit record;
7. показать каждое расхождение по пути JSON.

В audit replay v0.2 полный повторный расчёт реализован для всех четырёх текущих расчётных модулей:

- **Quick EQD**;
- **Compare Regimens**;
- **Treatment Gap** — включая календарь/ручную длительность, стратегии компенсации и OAR cards;
- **Reirradiation** — включая cumulative BED/EQD₂, recovery assumptions, remaining EQD₂ budget и HyTEC assessment, если он присутствовал в исходном аудите.

Replay отдельно показывает:

- сохранённую и текущую версию движка;
- сохранённую и текущую evidence dataset version;
- факт изменения версий;
- результат фактического сравнения.

Совпадение replay означает только воспроизводимость расчёта из сохранённых входных данных. Оно не является новой клинической валидацией.

### Особенности replay schema 1.0

Для Treatment Gap при сравнении ошибок OAR проверяются сам статус ошибки и сохранённые входы, а не локализованный текст сообщения. Текст ошибки относится к представлению интерфейса и может меняться между RU/EN без изменения физического смысла расчёта.

В ранней schema 1.0 Reirradiation сохранял полный HyTEC assessment, но не отдельный boolean подтверждения `thecal-sac Dmax`. Поэтому при replay исторического schema 1.0 это подтверждение восстанавливается из сохранённой причины применимости assessment. Для integrity-verified envelope это детерминированно; для legacy raw JSON исходный файл всё равно остаётся `legacy-unverified`.

Следующая версия audit schema должна хранить такие пользовательские подтверждения отдельными входными полями, чтобы не восстанавливать их из assessment metadata.

## Безопасность

Экспортированный файл документирует расчёт поддержки клинического решения.

Он не является:

- назначением лечения;
- автоматическим заключением о безопасности;
- заменой независимой проверки;
- заменой клинического протокола или ограничений доза–объём.
